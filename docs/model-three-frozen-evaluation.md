Do not launch the broader panels below. The direct-comparison source and artifacts will be integrated after their separate handoff; no comparison outcomes are asserted here.

Seeds 94301–94304 are held out from all collection, demonstrations, development and checkpoint selection. Development checks use 94401–94404; the existing four qualification teacher wins are development evidence only. All seeds are reserved to this task and must be excluded from trainer seed generation.

Use the same pinned native opponent deck and both seat orders for every policy package. Model3 and the frozen BC warm-start each face scripted teacher, frozen Model2 and legal-random ordinary actions. Model2 additionally faces the teacher as a historical control. This is 56 planned games, two native workers total, a two-hour global evaluation cap, 240 seconds/500 commands per game, and no replacement cases. Run panels in manifest order; interrupted or unattempted panels remain missing. Parent coordinates an exclusive rollout window after training. No rollout has been launched by this evaluation task.

PPO versus its own BC warm-start is the primary learning-from-experience comparison. Both must use the same frozen learned selection policy and helpers; report ordinary PPO decisions, learned selection decisions and helper decisions separately. Model2 must use its original 32/27 encoder and frozen checkpoint SHA-256 `144180ba472cfe23e405eb7c47448e5c88e8148ac5440c5d38f37a54d7ad690b`. Model3 uses 224/191 `native-card-action-features/1`. Model2 prompt helpers differ from Model3 selection policy, so Model2 comparisons describe entire policy packages and cannot isolate PPO learning.

Freeze the selected PPO checkpoint, BC ordinary and selection checkpoints, executable/source hashes, exact training recipe/seeds and stopping rule before exposing heldout outcomes. Use predeclared development evidence for learning-signal checks. Record policy/value losses, KL, clipping, entropy, finite gradients, changed parameters, reload parity, fresh inference and development terminal outcomes. These establish learning implementation and observed development changes separately from strength. Never select a later checkpoint or retrain because of final results.

Report W/L, terminal-without-winner, command truncations, wall timeouts, cancellations, unattempted games and fatal errors separately, per opponent and seat. An absent winner is unknown, not a draw. A command cap is truncation, not a loss. Preserve losing journals and all partial decision/progress traces; naturally terminal journals can be replayed using the original pins. Correctness/privacy/provenance errors invalidate the affected comparison and stop the run. No incomplete games enter training.

Report pair means and seed-cluster uncertainty, with all four seed rows visible. Reuse `pairSummary` from `src/evaluation-suite.mjs` for descriptive paired bootstrap (seed 1729, 10,000 resamples); with four clusters this may collapse to zero width and cannot support superiority. For an honest distribution-free 95% interval on a mean score use radius `sqrt(log(40)/(2*n))`, clipped to [0,1]. For PPO-minus-BC seed-cluster differences use radius `sqrt(2*log(40)/n)`, clipped to [-1,1]. At n=4 these bounds are wide; improvement will normally be inconclusive. The frozen improvement rule requires complete comparisons, valid integrity gates and the paired difference lower bound above zero. Four clusters cannot satisfy that conservative rule. Report observed changes without strength claims. Missing outcomes may be assigned [0,1] bounds solely to show sensitivity; never label them as losses/draws.

## Reusable entrypoints and exact APIs

The existing native harness remains the execution path:

```powershell
node scripts/card-action-rollout.mjs <private-native-config.json> <fresh-run-name> <private-panel-plan.json>
```

`runCardActionRollout(configPath, name, planPath)` exports the same API. A panel plan has `schema: native-card-action-rollout-plan/1`, `mode: evaluate`, `workers: 2`, `maximumWallSeconds: 1200`, `maximumGameSeconds: 240`, `maximumGameCommands: 500`, `teacherMix: 0`, absolute CPU `modelConfig`, and eight tasks from the manifest. Each task is `{id, seed, split: 'evaluation', policySeat, seatOrder}`; deck zero must follow `policySeat` across the seat swap. Copy printing aliases and diagnostic action keys from the prepared profile plan. Keep private checkpoint copies inside this checkout's ignored `runs/`, as required by current admission.

Opponent choices already supported by the harness: `opponentModelConfig` plus `opponentModelKind: native-v2` for Model2; `opponentPolicy: teacher` for the pinned native config policy; `opponentPolicy: legal-random` for seeded uniform ordinary actions with the same pinned prompt helper. For Model2 as subject use `modelKind: native-v2`. NativeModelClient owns the Model2 encoder; do not adapt its weights into the Model3 encoder. The teacher module is pinned by `native-config.policySha256`; retain its exact bytes.

`runAuditedEpisode(config, options)` in `integrations/local-worker/audit-runner.mjs` supplies `decideOrdinary({seat, view})`, `decidePrompt({seat, view, validate})`, `onAcceptedDecision({seat, view, decision, ordinaryPolicyUsed, promptPolicyUsed})`, `onFrame(...)`, `seed`, `seatOrder`, `boundaryEvery: 1`, `strictCommands: true`, `maxCommands` and `maxSeconds`. Its terminal result is `{journal, summary}` with `summary.completedNaturally`, `winnerSeat`, `commands`, `boundaryChecks` and `terminalStateHash`. Replay uses `{seed, seatOrder, replay: journal}` with the original config and no decision callbacks. Do not pass audit authority into policy callbacks.

Current inference clients expose `verify()`, `decide({view})`, `shutdown()` and (CardActionModelClient) `rankChoices({view,prompt})`. PPO worker/integrator must provide an adapter with these contracts and a separately pinned BC selection client, or wire those two clients into the existing callback hooks. The old CardActionModelClient launches `card_action_torch.py`; it does **not** automatically load a new PPO actor-critic checkpoint. Do not claim the final PPO evaluation entrypoint is admitted until that adapter passes schema, checkpoint, deterministic inference and decision-count checks. Keep the same runner and receipt structure.

Each private panel retains `plan.json`, source snapshot, fixed checkpoint copies, `receipt.json`, and per-case `journal.json`, `decisions.jsonl`, `case-receipt.json` or `failure.json`. Before each panel, subtract elapsed evaluation time from the two-hour global cap; stop without replacements when exhausted. Publish safe aggregate metrics and hashes locally in Git; weights, native programs/assets, actor views and private runtime configs stay ignored.
